## 项目总览（开场 30 秒自我介绍）

> 我做的是一个「气象大数据 + AI 智能体」的出行推荐系统，后端 Python FastAPI，前端 React/Vue，数据库 PostgreSQL + TimescaleDB + pgvector + PostGIS，AI 层用 LangGraph + MCP + RAG。核心亮点是：把天气数据、资讯、知识库、联网搜索、用户私有行程做成了一套可插拔的工具，让 AI Agent 能自动决策调用，实现「查天气 → 查知识 → 查行程 → 结合天气给出行提醒」的完整链路。

**技术栈速记**：
- 后端：FastAPI + SQLAlchemy 2.0 异步 ORM + Celery + Redis
- 数据库：PostgreSQL 17 + TimescaleDB（时序）+ pgvector（向量）+ PostGIS（地理）
- AI：LangGraph（状态机）+ MCP（工具协议）+ RAG（检索增强）+ 智谱 embedding-3 + DeepSeek（可切换）
- 前端：React19 + Vite + TS（用户端）、Vue3 + Vite + TS（管理端）

## Day 2 · 数据库设计

**做了什么**：6 张表 + 三大 PG 扩展 + Alembic 迁移。

**底层原理（重点讲）**：
1. **TimescaleDB**：时序数据（天气历史）的专用扩展，本质是把大表按时间列自动分区成多个 chunk（超表 hypertable）。查询某段时间的数据时只需扫描相关 chunk，比普通 B-tree 快一个量级。关键操作 `create_hypertable('weather_history', 'time')`。
2. **pgvector**：给 PostgreSQL 加向量类型 `vector(1024)`，支持 `<=>` 余弦距离算子 + HNSW 索引做近似最近邻（ANN）检索。相比专用向量库（Milvus）省运维，数据量小够用。
3. **PostGIS**：地理空间扩展，为 3D 地标（经纬度）提供空间查询能力。

**关键参数**：
- 向量维度固定 `1024`（与智谱 embedding-3 的 dimensions=1024 对齐）
- HNSW 索引用 `vector_cosine_ops`（余弦相似度算子）

**踩坑（很能体现工程能力，必讲）**：
- Docker 镜像源失效 → 改用本地已有 `pgvector/pgvector:pg17` 为基础镜像，通过 PGDG 源装 postgis、TimescaleDB 官方源装 timescaledb，`docker commit` 成自定义镜像。
- timescaledb 需 `shared_preload_libraries` 预加载，否则 `CREATE EXTENSION` 报错。

**面试官追问**：
- Q：「为什么用 TimescaleDB 不用普通表？」
  A：天气数据是典型时序数据（每小时的温度/湿度），TimescaleDB 自动分区 + 时间维度压缩 + 连续聚合，查询性能和存储都优于普通表。
- Q：「向量维度为什么是 1024？」
  A：embedding-3 支持自定义维度，1024 是精度和存储/检索速度的平衡点，也统一了全库向量格式。

## Day 3 · 基础业务接口

**做了什么**：统一响应体、全局异常、JWT 鉴权、用户/资讯/反馈 CRUD。

**核心实现（底层逻辑）**：

1. **统一响应体**：`{code, message, data}`，`code=0` 成功。业务错误也返回 HTTP 200 + 业务 code（前端按 code 判断），方便移动端统一拦截。

2. **密码哈希（不用 bcrypt，讲得出门道）**：
   - 用标准库 `hashlib` 实现 **PBKDF2-HMAC-SHA256**，10 万次迭代 + 16 字节随机盐
   - 存储格式 `pbkdf2$sha256$<salt>$<hash>`
   - 校验用 `hmac.compare_digest` **常量时间比较**，防时序攻击（timing attack）
   - **为什么不引入 passlib/bcrypt**：离线环境安装受限，用标准库实现同等强度

3. **JWT 无状态鉴权**：
   - payload：`sub`（用户ID）+ `iat` + `exp` + `role`
   - HS256 签名，`Authorization: Bearer <token>`
   - FastAPI 依赖注入：`CurrentUser`（必须登录）/ `OptionalUser`（可匿名）

4. **关键修复（体现深度）**：`TimestampMixin` 的 `created_at/updated_at` 原来只用 `server_default`（数据库侧生成），导致 Pydantic 序列化时触发 `MissingGreenlet` 错误（异步 ORM 在非 async 上下文访问需懒加载的属性）。修复：同时加 Python 侧 `default`/`onupdate`，值在内存中就写好了。

**面试官追问**：
- Q：「JWT 和 Session 有什么区别？为什么选 JWT？」
  A：JWT 无状态，服务端不存会话，适合前后端分离和水平扩展；缺点是无法主动失效（logout 只是前端删 token）。Session 需服务端存储，但可主动踢人。
- Q：「密码为什么用 PBKDF2 不用 MD5？」
  A：MD5 快且可被彩虹表/GPU 暴力破解；PBKDF2 通过大量迭代故意拖慢计算，增加暴力破解成本。更现代的还有 bcrypt/scrypt/argon2。

## Day 4 · 气象数据源接入

**做了什么**：接 Open-Meteo 拉真实天气，写 TimescaleDB 时序表，Celery 定时同步。

**实现链路**：
```
Celery beat（每小时第5分钟）→ sync_weather_hourly
  → fetch_and_store() → Open-Meteo API（实时+7天预报）
  → 解析 WMO weather_code → 中文描述
  → upsert 写 weather_history（ON CONFLICT (time, location_code) DO UPDATE）
```

**关键点**：
- **WMO 天气编码映射**：Open-Meteo 返回数字 code（0=晴，95=雷阵雨），需映射成中文
- **预警兜底**：Open-Meteo 对中国无官方预警，按阈值生成（风速≥40km/h 大风、降水≥10mm 降水提示）
- **upsert 去重**：`INSERT ... ON CONFLICT DO UPDATE`，重复同步不产生重复行

**Celery + asyncpg 踩坑（必讲，含金量高）**：
- 问题：Celery 任务里用 `asyncio.run()` 执行 async 代码，第一次成功，第二次报 `'NoneType' object has no attribute 'send'`。
- 根因：asyncpg 连接绑定在 `asyncio.run()` 创建的一次性事件循环上，循环关闭后连接失效。
- 修复：① 用 `NullPool` 独立引擎（不跨任务复用连接池）；② 模块级复用事件循环（`_get_loop()` + `run_until_complete`）替代反复 `asyncio.run`。

**面试官追问**：
- Q：「为什么用 Celery 不用直接写库？」
  A：同步天气是耗时 IO 操作，不能阻塞 HTTP 请求；Celery 异步解耦，且 beat 支持定时调度。
- Q：「Windows 下 Celery 有什么坑？」
  A：Windows 不支持 fork，要用 `-P solo` 池；prefork 会有 spawn 问题。

## Day 5 · 数据清洗模块

**做了什么**：上传脏 CSV → Celery 异步清洗 → 四类规则 → 下载结果。

**四类清洗规则（核心）**：
1. **去重**：`drop_duplicates(keep="first")`
2. **缺失填充**：数值列中位数、分类列众数
3. **异常过滤**：数值超出合理范围置 NaN（温度[-50,60]、气压[800,1100]）
4. **单位标准化**：后缀规则识别（`_f`→华氏转摄氏、`_kpa`→kPa 转 hPa、`_ms`→m/s 转 km/h）

**关键踩坑（顺序问题，必讲）**：
- 初版把「列名别名映射」放「单位标准化」之前，导致 `temp_f` 先被映射成 `temperature` 后，`_f` 后缀丢失，单位转换失效。
- 修复：**先单位标准化（基于原始列名后缀），再别名映射**。

**面试官追问**：
- Q：「缺失值为什么数值用中位数不用均值？」
  A：中位数对异常值鲁棒，不受极端值影响；均值会被离群点拉偏。
- Q：「怎么判断异常值？」
  A：业务规则定义合理物理范围（温度不可能 999），超出即异常；更高级可用 3σ 或 IQR。

## Day 6 · RAG 知识库底座

**做了什么**：16 篇广州知识文档 → 分块 → 智谱 embedding → pgvector 存储 → 语义检索。

**RAG 完整链路（底层原理，重点）**：
```
离线建索引：
  文档 → 切块(chunk=300字, overlap=50) → 智谱 embedding-3(1024维) → 写 pgvector

在线检索：
  用户问题 → embedding → 余弦相似度(<=>) → TopK 片段 → 拼进 prompt 给 LLM
```

**关键参数**：
- `EMBED_CHUNK_SIZE=300`（块大小）、`EMBED_CHUNK_OVERLAP=50`（重叠，防止语义在切点截断）
- `EMBED_BATCH_SIZE=16`（批量向量化，控制请求大小）
- `EMBED_DIM=1024`、`EMBED_TOP_K=5`

**分块为什么要 overlap（讲得出门道）**：切块会切断上下文，块边界处的句子可能被拆成两半，导致语义丢失。相邻块重叠 50 字，保证边界信息在至少一个块里完整。

**降级设计**：智谱 API 失败/无 Key 时，用**确定性本地伪向量**（3-gram hash + L2 归一化）兜底，保证离线可联调、维度恒 1024。

**面试官追问**：
- Q：「RAG 和微调的区别？为什么选 RAG？」
  A：RAG 知识可随时更新（改文档即可）、成本低、可溯源（能指出引用了哪段）；微调需重新训练、更新困难、且可能"遗忘"旧知识。
- Q：「向量检索为什么用余弦相似度？」
  A：余弦衡量方向而非长度，对文本 embedding 更合适（语义由方向表达，文档长短不影响）。pgvector 的 `<=>` 就是余弦距离。
- Q：「embedding 维度对检索有什么影响？」
  A：维度越高表达能力越强但存储和计算越贵；1024 是常见平衡点。

## Day 8 · LangGraph Agent 框架

**做了什么**：接 DeepSeek，搭 LangGraph 状态机，实现意图识别 + 生成。

**核心概念（必讲）**：
- **LangGraph**：把 Agent 建模成「有状态、可循环、可分支」的图（state machine），比 LangChain 的线性 Chain 强在能表达动态流程。
- **AgentState**：会话状态容器 `{messages, intent, answer, error}`，`add_messages` 累加合并。
- **图结构**：`START → classify_intent → generate → END`，附 `handle_error` 兜底节点。

**关键参数**：
- `temperature=0.3`（对话稳定性，0 最保守 1 最发散）
- `timeout=60s`、`max_retries=2`

**多模型抽象层（重要亮点）**：
- `get_llm(provider)` 支持 deepseek/qwen/zhipu/openai/moonshot/ollama 6 个 **OpenAI 兼容格式**提供商
- `_PROVIDERS` 字典映射 + 多实例缓存 + 空 Key 降级
- 为什么只选 OpenAI 兼容格式：统一走 `langchain-openai` 的 `ChatOpenAI`，避免给 Claude 等接不同适配器

**面试官追问**：
- Q：「LangGraph 和 LangChain 的区别？」
  A：LangGraph 是 LangChain 生态的一部分。LangChain 的 LCEL 是线性管道，LangGraph 是有状态图，支持循环/分支/回退。Agent 需要"判断意图→决定调哪个工具→可能循环重试"，用图表达更自然。
- Q：「temperature 影响什么？」
  A：控制采样的随机性。低值输出更确定（适合意图识别、工具调用），高值更有创造性（适合创意写作）。

## Day 9 · MCP 工具层封装

**做了什么**：把天气/预报/资讯封装成 MCP Server，Agent 通过 MCP 协议自动调用。

**核心概念（重点，必讲）**：
- **MCP（Model Context Protocol）**：Anthropic 提出的 AI 调用工具的**标准协议**。让工具变成可插拔的服务，AI 统一用这套协议发现和调用，不关心工具背后实现。
- **MCP Server**：独立进程，注册 3 个工具（get_weather/get_forecast/search_news）
- **双传输模式**：stdio（本地开发，拉起子进程）/ streamable-http（上线，独立 HTTP 服务）

**关键实现**：
- `langchain-mcp-adapters` 的 `MultiServerMCPClient` 动态加载工具
- stdio 模式用 `sys.executable`（venv Python）拉起子进程，否则系统 Python 没装 mcp 包
- ReAct 式工具循环：`agent ⇄ tools`，直到 LLM 不再发起 tool_call

**架构价值（面试亮点）**：
- 工具层与 Agent 解耦，增删工具只需改 MCP Server，Agent 端零改动
- 天气数据源可配置切换（qweather/open_meteo）+ 失败自动降级

**面试官追问**：
- Q：「MCP 和 function calling 有什么区别？」
  A：function calling 是模型能力（让模型输出结构化的工具调用），MCP 是**工具接入的标准化协议**（怎么连接、发现、描述工具）。两者配合：MCP 提供工具，模型用 function calling 决定调哪个。
- Q：「stdio 和 HTTP 传输怎么选？」
  A：本地同机用 stdio（简单稳定），生产/跨机用 streamable-http（可独立部署扩容）。

## Day 10 · RAG 接入 + 自动决策 + 联网搜索 + 私有知识库

**做了什么**：完整链路打通 + ReAct 决策 + 多租户 RAG + 联网搜索。

### 1. 完整链路
```
用户提问 → 意图识别 → LLM 决策 → 工具调用（MCP/RAG/联网）→ LLM 生成答案
```

### 2. ReAct 决策（三路径）
- **信息不足 → 反问**（缺城市/日期，礼貌追问）
- **需实时数据 → 调工具**（天气/知识/资讯/联网）
- **可直答 → 直答**（闲聊）

**实现**：决策规则写在系统提示词里，让 LLM 自主判断，不是硬编码 if-else。LangGraph 条件边构成循环。

### 3. 联网搜索（Tavily 优先 + DuckDuckGo 兜底）
- Tavily：AI 场景搜索引擎，返回结构化结果
- 处理知识库/天气覆盖不到的实时信息（景区开放、门票、时事）

### 4. 用户私有知识库（多租户 RAG）
- `user_knowledge` 表，`user_id` 隔离
- 上传/检索/列表/删除接口

### 5. 行程天气提醒（最有产品价值的功能）
```
用户上传结构化行程（日期/时间/地点/活动）
  → 问"明天有什么安排"
  → 解析日期 → 取行程 → 查当天天气 → LLM 生成逐条提醒
```

### 关键架构决策（必讲，体现深度）

**为什么私有检索走「本地工具」不走 MCP？**
- MCP 工具跑在独立子进程（stdio），`contextvars` 用户上下文跨不了进程，拿不到 user_id
- 解决：无状态公共工具走 MCP，有用户态的私有检索走 Agent 本地工具，用 contextvar 透传 user_id
- 这体现了「按工具是否带用户态分层」的架构思考

**contextvars 的作用**：
- 类似线程局部变量（thread-local），但基于 asyncio 上下文，天然支持并发隔离
- 每个请求在独立 context 里设置 user_id，工具内部读取，互不干扰

**四层降级（保证接口永不 500）**：
1. embedding 失败 → 本地伪向量
2. 意图识别失败 → 关键词规则
3. LLM 生成失败 → handle_error 节点
4. 最外层 chat() → catch 一切异常

**面试官追问**：
- Q：「多租户 RAG 怎么保证数据隔离？」
  A：每个文档分块记录 `user_id`，检索 SQL 强制 `WHERE user_id = :uid`，从查询层面隔离，不可能查到别人的数据。
- Q：「为什么行程要结构化存储，不用纯文本？」
  A：行程天气提醒需要精确的日期/地点/活动字段来匹配天气，纯文本切块后丢失结构化信息。结构化字段解析准、不出错。
- Q：「联网搜索什么时候触发？」
  A：系统提示词里明确规则——实时性/时效性信息（景区当天开放、最新门票、时事）且知识库天气覆盖不到时，调 web_search。

## 全项目通用追问（高频）

**Q1：整个 AI 助手的核心链路用一句话描述？**
A：LangGraph 状态机驱动，先意图识别，再让 LLM 决策（反问/调工具/直答），工具通过 MCP 协议可插拔接入，RAG 提供知识检索，最终 LLM 融合真实数据生成答案。

**Q2：为什么用 LangGraph 而不是直接写 if-else？**
A：对话流程是动态不确定的，if-else 写死难维护。LangGraph 让 LLM 自主决策路由，图结构可视化、可测试，且支持循环（工具调用后继续推理）。

**Q3：整个系统怎么保证稳定（降级/容错）？**
A：四层降级 + 工具错误兜底 + 数据源可切换（和风挂了自动切 Open-Meteo，Tavily 挂了切 DuckDuckGo）+ Celery 异步解耦 + JWT 无状态可扩展。

**Q4：API Key 怎么管理？**
A：只存后端 `.env`，`.gitignore` 忽略，绝不硬编码/暴露前端/提交 git。这是安全底线。

**Q5：如果让你优化，最想改进哪里？**
A：① 和风 Key 生效后切换（国内天气更准）；② 行程提醒支持跨城市天气（现在固定广州）；③ 意图分类扩展（资讯类独立）；④ 加对话历史记忆（现在是单轮）；⑤ 流式输出（SSE）提升体验。

## Skill 规范化（Day 12 追加，重点）

### 什么是 Skill（一句话）
Skill 就是**把"一项能力"打包成一个文件夹**，里面包含：说明文档（SKILL.md）+ 参考资料（references/）+ 可执行逻辑（scripts/），让 AI 能理解"什么时候用、怎么用"。

### 标准结构（Anthropic Agent Skills 规范）
```
backend/skills/
├── travel_planning/            # 一个 Skill = 一个文件夹
│   ├── SKILL.md                # 说明书：何时用 + 怎么用
│   ├── references/             # 参考资料（规则表 markdown）
│   │   └── scoring-rules.md
│   └── scripts/                # 可执行逻辑（纯函数）
│       └── route_planner.py
```

### 三个部分各有什么用
| 部分 | 作用 | 类比 |
|------|------|------|
| SKILL.md | 告诉 AI"这个能力是干嘛的、何时触发" | 岗位职责说明书 |
| references/ | 存放规则/知识（markdown） | 参考资料库 |
| scripts/ | 真正干活的代码（纯逻辑） | 具体执行的人 |

### Skill 与 MCP 的关系
- **Skill** = 能力的"知识和逻辑"（文件夹形式，可维护）
- **MCP** = 能力的"对外调用入口"（让 Agent 能自动触发）
- 两者配合：Skill 定义"做什么、怎么做"，MCP 定义"如何被 AI 发现和调用"

### 面试怎么说
> "我按 Anthropic Agent Skills 规范把技能组织成标准文件夹结构，每个 Skill 有 SKILL.md（frontmatter 描述何时用）、references/（规则文档）、scripts/（可执行逻辑），再用 skill_loader 统一扫描解析。MCP 工具作为调用入口，让 Agent 通过协议自动发现和触发这些 Skill，实现了能力层（Skill）与调用层（MCP）的解耦。"

### 为什么目录用下划线
- Python import 不支持连字符（`import travel-planning` 报错），所以目录用 `travel_planning`
- 但 SKILL.md 里的 name 字段用连字符 `travel-planning`，符合 Anthropic 规范（URL 友好）

### 面试官可能追问
- Q：「Skill 和普通函数/工具有什么区别？」
  A：普通函数只有代码；Skill 是"代码 + 说明 + 参考资料"的完整打包，让 AI 能理解语义和触发条件，可维护性、可发现性更强。
- Q：「Skill 里逻辑放 scripts，规则放 references，为什么不都写代码里？」
  A：规则（温度档位、场景建议）用 markdown 放 references，改规则不用动代码、还能被 RAG 索引；脚本保持纯逻辑，职责清晰。

## 术语速查表

| 术语 | 一句话解释 |
|------|-----------|
| LangGraph | 用「图」建模 AI Agent 的框架，支持状态/循环/分支 |
| MCP | AI 调用工具的标准化协议（Anthropic 提出） |
| RAG | 检索增强生成：先查资料再回答，减少幻觉 |
| ReAct | 推理+行动循环：AI 边思考边调工具 |
| embedding | 把文本转成向量，语义相近的向量距离近 |
| pgvector | PostgreSQL 的向量扩展，支持余弦检索 |
| TimescaleDB | PostgreSQL 的时序扩展，自动按时间分区 |
| Celery | Python 异步任务队列，配合 Redis 做 broker |
| JWT | 无状态鉴权令牌 |
| contextvars | asyncio 下的上下文变量，替代 thread-local |
| temperature | 模型采样随机性参数 |
| HNSW | 近似最近邻索引算法，加速向量检索 |
| PBKDF2 | 基于口令的密钥派生函数，用于密码哈希 |
| upsert | INSERT ON CONFLICT，存在则更新否则插入 |
