## TL;DR

1. **名词之所以让人焦虑，是因为它们被平铺着念出来**。真实情况是：这些词分属**四个层次**，把它们按层次摆好，90% 的困惑会自动消失。
2. **层次是**：模型层（LLM / Token / Context / 多模态）→ 增强层（Embedding / RAG / 微调）→ 编排层（Agent / ReAct / LangGraph / 工作流）→ 接入层（Function Calling / MCP / Skill）。
3. **最消耗人的其实不是难词，是同义词**。"大模型 / LLM / GPT"是一个东西，"Agent / 智能体 / 助手"是一个东西，"工具调用 / Function Calling / Tool Use"是一个东西——**但"Agent 和 Workflow"不是**，这两个必须分清。
4. 每个名词我都配了**项目里的真实出处**，所以它不是一份背诵清单，而是能对照代码验证的索引。

## 一、先给你一张地图

我观察到一个现象：大部分"AI 名词焦虑"不是因为记不住，而是因为**这些词被以错误的顺序抛出来**。

比如有人一上来就跟你说"我们用了 ReAct 搭 Agent，通过 MCP 接工具，底层是 RAG 增强的 LLM"。这句话里混了四个层次的东西。你没听懂，不代表你笨——是这句话本身没有结构。

真实的结构是这样的（自下而上四层）：

```
┌──────────────────────────────────────────────────┐
│ ④ 接入层   Agent 怎么用上外部能力                  │
│    Function Calling · MCP · Skill · Tool Use     │
├──────────────────────────────────────────────────┤
│ ③ 编排层   怎么把一次问答变成"多步做事"            │
│    Agent · ReAct · 工作流 · LangGraph · 状态机     │
├──────────────────────────────────────────────────┤
│ ② 增强层   怎么让模型知道它训练时没见过的东西       │
│    Embedding · 向量库 · RAG · 微调 · Rerank       │
├──────────────────────────────────────────────────┤
│ ① 模型层   那个"会说话的东西"本身是什么            │
│    LLM · Token · Context Window · 提示词 · 多模态  │
└──────────────────────────────────────────────────┘
```

**记住这个顺序，比记住任何一个名词都有用**：下层是基础，上层是组合。上面每一层都建立在下面一层之上，不存在"跳过模型层直接聊 Agent"这回事。

接下来逐层说。每个词我都给：**一句话解释 + 项目里的真实出处**（可以对照代码看）。

## 二、模型层：最底层的那几个词

### LLM（大语言模型）

**一句话**：一个根据上文预测下一个词的函数，只是它见过的文本足够多，于是看起来像"懂了"。

我们平时说的"大模型""GPT""Claude""DeepSeek""通义千问"，**都是 LLM**。"GPT"只是 OpenAI 的一个产品名，不是术语。把它当术语用，容易显得不专业。

**项目里的出处**：`backend/app/services/llm_client.py`。这个项目不写死任何一家，而是只收"OpenAI 兼容格式"的模型：

```python
# 提供商 → 配置字段名映射（api_key / base_url / model）
_PROVIDERS: dict[str, tuple[str, str, str]] = { ... }
```

```python
    - 缓存键是 provider+model：同一提供商的不同模型（文本 vs 视觉）必须各存一份，
```

**为什么这行注释值得单独说**：它揭示了一个常被混淆的点——**同一个厂商的"文本模型"和"视觉模型"是两个模型**。项目的默认对话模型 `deepseek-chat` 是纯文本的，直接塞图片会返回 400。所以这里要单独配一个视觉模型（`glm-4v-flash`）。这就是"多模态"那件事。

### Token（词元）

**一句话**：模型处理文本的最小单位。不完全等于字，也不完全等于词。

中文里大概 **1 个 token ≈ 1~2 个汉字**（取决于分词器）。为什么要在乎它？因为**计费按 token、上下文长度限制也按 token**。

**一个容易踩的坑**：很多人以为"几百字的提示词不占地方"。但一个带 7 个工具定义的 Agent，每个工具的参数说明都是 schema 文本，**这些也全是 token**。项目里有个刻意的优化就是为此：

```python
# 只有 weather/travel/outfit/knowledge 才 bind_tools，闲聊类不绑
# → 少注入工具 schema，省 token
```

**闲聊时不给模型塞工具说明**——这是省钱，也是降低干扰。

### Context Window（上下文窗口）

**一句话**：模型一次能"看见"的最大 token 数。超出就看不见了，**不是变慢，是直接看不见**。

这是初学最容易误解的一个：上下文不是"内存"，它没有分页机制。塞不下的内容会被直接丢弃（或被截断）。

**项目里的出处**：多轮对话只取最近 10 条历史：

```python
HISTORY_LIMIT = 10   # 历史按 role 还原，只取最近 10 条防上下文爆炸
```

**为什么是 10 而不是"全部"**：因为每多一轮，输入 token 就线性增长，成本也跟着涨。而且早期对话对当前问题通常已经没用了。这是一条"用工程手段换成本"的取舍。

### 提示词 / Prompt

**一句话**：你给模型的那段输入。

分三种角色，这个区分很重要：

| 角色 | 是什么 | 类比 |
|---|---|---|
| System（系统提示词） | 设定身份与规则，**优先级最高** | 员工手册 |
| User（用户） | 当前的问题 | 客户的诉求 |
| Assistant（助手） | 模型之前的回答（多轮时用来维持上下文） | 员工之前的回复 |

**项目里最深的一个用法**：把决策规则直接写进 System Prompt，而不是用 if-else 硬编码：

> 项目里有 9 条决策规则（何时调哪个工具、何时反问、何时直答）全部写在 `GENERATE_SYSTEM_PROMPT` 里，让 LLM 自主路由。

这是"提示词即决策引擎"——也是为什么第 06 篇的标题叫《删掉 if-else》。但要注意一个前提：**提示词是"建议"，不是"保证"**。第 13 篇里那句"不把模型会听话当作正确性依赖"说的就是这个。

### 多模态（Multimodal）

**一句话**：模型除了文字，还能处理图片、音频、视频。

**项目里的出处**：图片走视觉模型（`glm-4v-flash`），语音转写走独立的 ASR 后端：

```python
    # 语音转写后端：
    #   none           —— 关闭（默认。没装模型时不假装支持，而是明确告诉用户怎么开）
    #   openai         —— 任意 OpenAI 兼容的 /audio/transcriptions
    #   faster_whisper —— 本地开源
    ASR_PROVIDER: str = "none"
```

**注意这里的设计哲学**："没装模型时不假装支持，而是明确告诉用户怎么开"。**能力缺失时要明说，不要静默降级**——这个原则后面还会反复出现。

### 幻觉（Hallucination）

**一句话**：模型一本正经地编造了不存在的事实。

**关键认知**：幻觉不是 bug，是**这个技术的固有特性**。模型的本质是"预测下一个最可能的词"，不是"查数据库"。所以它在不知道的时候，**会生成一个"看起来最像答案"的东西**，而不是说"我不知道"。

**项目里的出处**：系统提示词里有一条硬约束：

> 「禁止编造数据，工具未返回的数据一律不得臆造」

以及那条踩出来的经验：单轮对话时模型会凭训练知识编造"明天 3 月 15 日"——**接上工具后**才解决，因为有了真实数据源。

**这就是 RAG 存在的根本原因**——下一节说。

## 三、增强层：让模型"知道得更多"

模型的训练数据有截止日期，也不知道你的业务知识。解决这个问题有两条路：**微调** 和 **RAG**。

### Embedding（嵌入 / 向量化）

**一句话**：把一段文本变成一个数字数组（向量），**语义相近的文本，向量距离就相近**。

这是整个"向量检索"世界的基石。举个直观的例子：把"广州地铁怎么坐"和"广州交通出行指南"分别变成 1024 个数字，它们在数学空间里的距离，会比和"广州天气"的距离更近。

**项目里的出处**：智谱 `embedding-3`，专门指定 1024 维：

```python
    EMBED_DIM: int = 1024  # 向量维度（与智谱 embedding-3 dimensions=1024 对齐，匹配 Vector(1024)）
```

**为什么维度必须对齐**：数据库里的列定义是 `Vector(1024)`。如果模型返回 1536 维，写库时直接报错。所以客户端里有一道校验：

```python
            # 校验维度，防止与 Vector(1024) 不匹配报错
            for v in vectors:
                if len(v) != self.dim:
                    raise ValueError(f"向量维度 {len(v)} 与预期 {self.dim} 不一致")
```

**这是"工程纪律"的典型**：不是等数据库报错，而是在入口就拦下来。

### 向量库 / 向量数据库（Vector DB）

**一句话**：专门存向量、并支持"找最相似的 N 个"的数据库。

常见的有 Milvus、Qdrant、Weaviate、Chroma、Pinecone，以及本项目的选择——**不引入独立向量库，用 PostgreSQL 的 pgvector 扩展**。

**为什么**：项目数据量不大（16 个文档、33 个分块），为了向量检索单独运维一个数据库不划算。pgvector 让向量和业务数据在同一个库里，**少一个组件就少一份运维**。

这是个很典型的架构判断：**技术选型不是选"最先进的"，而是选"当前量级下最省事的"**。

### RAG（检索增强生成）

**一句话**：**先查资料，再回答**。Retrieval-Augmented Generation。

拆开看这个名字，它把三件事说明白了：

```
Retrieval（检索）  →  从知识库里找出相关片段
Augmented（增强）  →  把片段拼进提示词（作为"参考资料"）
Generation（生成） →  模型基于这些真实材料来回答
```

完整链路（项目里是双阶段的）：

```
【离线】文档 → 分块 → Embedding → 存入 pgvector
【在线】问题 → Embedding → 余弦检索 Top-5 → 拼进 Prompt → LLM 生成
```

**RAG 解决的三个问题**：① 知识可以热更新（改文档就行，不用重训模型）② 可溯源（能指出引用了哪一段）③ 成本低。

**项目里的出处**：`backend/app/services/rag_service.py`。检索用的是余弦距离 `<=>`：

```sql
SELECT title, source, content, chunk_index,
       1 - (embedding <=> '{vec_literal}'::vector) AS similarity
FROM knowledge_chunks
WHERE embedding IS NOT NULL
ORDER BY embedding <=> '{vec_literal}'::vector ASC
LIMIT :top_k
```

**分块（Chunking）** 是 RAG 里最容易被低估的一步：文档太长塞不进上下文，所以要切。项目用 300 字一块。**切得好不好，直接决定检索质量**——第 13 篇里那个 `overlap` 静默失效的坑就在这一步。

### Rerank（重排）

**一句话**：先粗筛出 20 条，再用一个更精细的模型挑出最相关的 5 条。

为什么要两步？因为**向量检索快但不精**（它是"语义大概像"），而重排模型慢但准。先粗后精，是检索系统的通用套路。

**项目里的出处**：这是列在开发计划里的**升级方向**，目前还没做（现在是直接取 Top-5）。我在第 04 篇里提过这个前瞻设计——**知道"计划做什么"和"现在有什么"的区别，是讲清楚项目的前提**。

### 微调（Fine-tuning）

**一句话**：拿自己的数据继续训练模型，让它"内化"这些知识。

**什么时候用微调而不是 RAG**？项目里的判断是：

| | RAG | 微调 |
|---|---|---|
| 知识更新 | 改文档即可 | 要重新训练 |
| 可溯源 | 能指出引用哪段 | 说不清 |
| 成本 | 低 | 高 |
| 适合 | **知识类、事实类** | **风格类、格式类** |

**一句话总结**：**要"知道什么"用 RAG，要"怎么说话"用微调**。出行助手需要的是"广州有哪些景点"这类知识，所以选 RAG。

## 四、编排层：让模型"会做事"

上面两层解决"模型知道什么"。这一层解决**"模型怎么一步步把事做完"**。

### Agent（智能体）

**一句话**：**LLM + 工具 + 循环**。

这是最简单也最准确的定义。一个裸的 LLM 只能"答话"；给它工具、再让它能"调完工具看结果、然后决定下一步"，它才变成 Agent。

关键在于那个**循环**。普通调用是：输入 → 输出 → 结束。Agent 是：

```
提问 → 模型决定调工具 → 执行工具 → 结果回给模型 → 模型决定下一步 → ...
                                                    ↑______（循环，直到不需要再调）
```

**项目里的出处**：`agent ⇄ tools` 这条条件边：

```
graph.add_conditional_edges(
    "agent",
    _should_continue,        # 有 tool_calls → tools；没有 → END
    {"tools": "tools", END: END},
)
graph.add_edge("tools", "agent")   # 工具执行完，回到 agent —— 这就是循环
```

**"有的话就继续，没有就结束"——Agent 的本质就这三行代码。**

### ReAct

**一句话**：**Reason + Act 的缩写**，就是上面那个"边推理边行动"的循环范式。

ReAct 不是某个框架，是一篇论文提出的**模式**：让模型先写出思考（Thought），再决定动作（Action），拿到观察结果（Observation），如此交替。

所以：**Agent 是"东西"，ReAct 是"模式"**。说"我用 ReAct 搭了一个 Agent"是通顺的；说"ReAct 和 Agent 哪个好"就不通了。

### 工作流（Workflow）與 Agent 的区别

**这是本篇最该记住的一组区别。**

| | 工作流 Workflow | Agent |
|---|---|---|
| 路径 | **人预先定好** | **模型自己决定** |
| 类比 | 流水线 | 老司机 |
| 可预测性 | 高 | 低 |
| 适合 | 步骤固定的任务 | 需要临场判断的任务 |

**Anthropic 有个很出名的观点**：能用工作流解决的，别上 Agent。因为 Agent 的"自主"是有代价的——不可预测、难测试、token 消耗大。

**项目里的体现**：这个项目其实**两者都有**。

- 意图分类 → 关键词匹配 → 路由，这是**工作流**（确定性的）
- 意图定下来后，让 LLM 决定调哪个工具，这是 **Agent**（自主的）

**"该确定的地方确定，该自主的地方自主"**——这是成熟的架构判断。

### LangGraph 与状态机

**一句话**：LangGraph 是**用"图"来描述 Agent 流程的框架**。

为什么需要图而不是链？因为链是线性的（A→B→C），而 Agent 需要**循环和分支**。

**项目里的出处**：整个 Agent 就是一张图，有四个节点：

```python
graph.add_node("classify_intent", _classify_intent)   # 识别意图
graph.add_node("agent", _agent_node)                  # LLM 决策
graph.add_node("tools", ToolNode(tools))              # 执行工具
graph.add_node("handle_error", _handle_error)         # 兜底
```

**状态机**指的是：这张图有一份**共享的状态**在节点间流转（项目里是 `AgentState`），每个节点读它、改它、然后把控制权交给下一个节点。

一个很实用的细节：状态里的消息列表用 `add_messages` 标注，**新消息会自动"追加"而不是"覆盖"**：

```python
messages: Annotated[list, add_messages]
```

这是 `Annotated` 在 Agent 场景里的经典用法——**告诉框架"这个字段怎么合并"**。

## 五、接入层：让模型"用得上外部能力"

模型决定"要调工具"了，但工具**怎么接进来**？这一层就是干这个的。

### Function Calling / Tool Use（工具调用）

**一句话**：**模型的一种能力——它能输出"我想调这个函数、参数是这些"这种结构化结果**。

**这是最容易被误解的一点**：模型**不执行**任何函数。它只是输出一个"调用意图"，真正执行的是**你的代码**。

```
模型输出：{"name": "get_weather", "args": {"city": "广州"}}
             ↓
       你的代码去真的调 API
             ↓
模型收到结果：{"temp": 28, "weather": "晴"}
             ↓
       模型基于这个结果生成回答
```

**关键认知**：Function Calling 是**模型能力**，它回答的是"**调哪个**"的问题。

### MCP（Model Context Protocol）

**一句话**：**一套标准协议，规定"工具怎么被描述、发现和调用"**。

**MCP 和 Function Calling 的区别**——这是面试高频题，也是本系列第 02 篇的核心：

| | Function Calling | MCP |
|---|---|---|
| 是什么 | 模型**能力** | 工具接入**协议** |
| 回答的问题 | 调**哪个**工具 | 有**哪些**工具、怎么连 |
| 类比 | 你会打电话 | 电话网络本身 |

**打个比方**：Function Calling 像是"你会用电话"；MCP 像是"电话网有自己的标准，任何电话都能接进来"。前者是个人能力，后者是基础设施。

**项目里的价值**：MCP 让工具**可插拔**。工具跑在独立进程里，增删工具时 **Agent 代码零改动**——重启一下自动重新发现。

**项目里的一个真实坑**：MCP 跑在独立子进程（stdio 传输），所以必须用 `sys.executable`（venv 的 Python），否则系统 Python 没装 `mcp` 包会直接报 `ModuleNotFoundError`。

### Skill（技能）

**一句话**：**把"一项能力"打包成一个文件夹**——说明书 + 参考资料 + 可执行逻辑。

结构（Anthropic Agent Skills 规范）：

```
skills/outfit_recommend/
├── SKILL.md                  # 说明书：何时用、怎么用
├── references/               # 规则表（markdown）
│   └── temp-rules.md
└── scripts/                  # 真正干活的代码
    └── outfit_engine.py
```

**Skill 和 MCP 的分工**：

- **Skill** 是能力的"**知识和逻辑**"（一个文件夹，可维护）
- **MCP** 是能力的"**调用出口**"（让 Agent 能自动发现和触发）

**一句话**：**Skill 定义"做什么、怎么做"，MCP 定义"如何被调用"。**

**为什么这个区分重要**：因为它解释了一个设计取舍——规则（比如"温度 ≥30℃ 建议轻薄面料"）放在 markdown 里，改规则**不用动代码**，而且这些 markdown **还能被 RAG 索引复用**。这正是第 13 篇说的"知识三分类"。

## 六、同义词辨析：这几组词真的是一回事

这部分最实用。会议上让你焦虑的，往往不是难词，而是**同一个东西被叫了三个名字**。

| 你听到的 | 其实是同一个东西 |
|---|---|
| 大模型 / LLM / GPT / 基座模型 | 都是指**那个会说话的东西** |
| 提示词 / Prompt / 指令 / Instruction | 你给模型的输入 |
| 工具调用 / Function Calling / Tool Use / 函数调用 | 模型输出"我要调 X"的能力 |
| Agent / 智能体 / 助手 / Bot | **LLM + 工具 + 循环** |
| 向量 / Embedding / 嵌入 / 特征向量 | 文本变成的那串数字 |
| 向量库 / 向量数据库 / Vector DB / 向量存储 | 存向量、查相似的那套东西 |
| 分块 / Chunking / 切片 | 把长文档切成小块 |
| 上下文 / Context / 上下文窗口 | 模型这次能看见的内容 |
| 知识库 / KB / 语料库 | 给 RAG 检索的那堆文档 |

**注意最后一列的写法**：我把每一组都归到了前面四层里的某一层。**先归层，再记名**——这是对抗名词焦虑最有效的方法。

## 七、必须分清的四组"近义词"

上面是"其实一样"，这四组是"**看着像，但完全不一样**"。混了会显得外行。

### ① Agent ≠ 工作流

前面详细说过。**Agent 的路径是模型决定的，工作流的路径是人定好的。**

### ② RAG ≠ 微调

**RAG 管"知道什么"（知识），微调管"怎么说话"（风格）。**

### ③ Skill ≠ 工具（Tool）

| | 工具 | Skill |
|---|---|---|
| 本质 | 一段**可执行代码** | 一套**文件夹**（说明 + 规则 + 代码） |
| 谁调它 | 模型按 schema 调 | 模型读说明后决定用，或按流程调脚本 |
| 有规则表吗 | 没有（只有参数） | **有**（`references/`） |

**一句话**：工具是"一个函数"，Skill 是"一项能力的完整打包"。

### ④ MCP ≠ Function Calling

前者是协议（有哪些工具），后者是能力（调哪个工具）。**这两个是最容易混、也最常被面试官问的。**

## 八、速查表

最后压成一张表。**建议先看"属于哪层"那一列**——理解了层次，名词就自动有位置了。

| 名词 | 属于哪层 | 一句话 |
|---|---|---|
| LLM | 模型层 | 预测下一个词的函数，见得多所以像懂了 |
| Token | 模型层 | 处理文本的最小单位，计费和长度限制都按它算 |
| Context Window | 模型层 | 一次能看见的最大 token 数，超了直接看不见 |
| Prompt | 模型层 | 你给模型的输入（System / User / Assistant 三种角色） |
| 多模态 | 模型层 | 除文字外还能处理图片、音频、视频 |
| 幻觉 | 模型层 | 一本正经地编造，是固有特性不是 bug |
| Embedding | 增强层 | 文本变向量，语义近则距离近 |
| 向量库 | 增强层 | 存向量、查最相似的 N 个 |
| RAG | 增强层 | 先查资料再回答，解决"不知道你的知识" |
| 分块 | 增强层 | 长文档切成小块，切法直接决定检索质量 |
| Rerank | 增强层 | 粗筛 20 条再精挑 5 条，快而不精 + 慢而准 |
| 微调 | 增强层 | 继续训练让知识内化，适合风格不适合知识 |
| Agent | 编排层 | **LLM + 工具 + 循环** |
| ReAct | 编排层 | 边推理边行动的**模式**（Reason + Act） |
| 工作流 | 编排层 | 路径由人定好，与 Agent 相对 |
| LangGraph | 编排层 | 用"图"描述 Agent 流程的框架 |
| 状态机 | 编排层 | 一份共享状态在节点间流转 |
| Function Calling | 接入层 | 模型输出"我要调 X"的**能力**（不执行） |
| MCP | 接入层 | 工具被描述/发现/调用的**协议** |
| Skill | 接入层 | 把一项能力打包成文件夹（说明 + 规则 + 代码） |
