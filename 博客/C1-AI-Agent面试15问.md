> 不是题库背诵。每道题都拆成「面试官想听什么 / 差答案长什么样 / 好答案怎么讲 / 可追问的下一层」，并用一个真实项目作答。

> 「AI Agent 工程化实战」· C 辑（面试问答）· C1
> 项目源码：**[Ticnix/weather-travel-recommend-system](https://github.com/Ticnix/weather-travel-recommend-system)**
> 基于气象大数据的出行推荐系统，AI Agent 全栈项目。FastAPI + PostgreSQL(TimescaleDB/pgvector/PostGIS) + Redis；
> LangGraph + MCP + Skill + RAG，对接 DeepSeek API；React/Vue 前后端分离，实现 3D 天气可视化、智能出行穿搭推荐。
> （项目仍在更新中）

## TL;DR

1. **AI 岗面试和传统开发岗最大的区别**：面试官**没法用白板题考你**。LLM 的行为不可复现，所以他会转向问"**你怎么知道它是对的**"。这句是我观察到的最高频考察意图。
2. 文章里的 15 道题分成**四种问法**：概念辨析（你懂不懂）、架构选型（你会不会做判断）、工程细节（你真做过吗）、踩坑复盘（你深不深）。
3. **第四类才是分水岭**。前三类背一背都能答；"你踩过什么坑"没法背——因为答案必须是**具体的、有代价的、你亲手修过的**。
4. 所以本文最实用的部分在第六节：**三个可以直接讲的真实事故**（`handle_error` 不可达、`overlap` 静默失效、两条建表路径）。这些答出来的效果，比背 20 个概念强。

## 一、先说面试官到底想听什么

很多人在 AI 岗面试里翻车，不是因为不会，而是因为**答错了层次**。

比如面试官问"RAG 和微调怎么选"，他**不是**想听你背定义。他想知道的是：

> **你在真实约束下做过取舍吗？**

同一个问题，三种回答的差距：

| 层次 | 回答 | 面试官判断 |
|---|---|---|
| 背定义 | "RAG 是检索增强，微调是继续训练" | 读过书，没做过 |
| 有结论 | "知识用 RAG，风格用微调" | 有判断力 |
| **有推导** | "我先排除了微调——因为我的知识（广州景点）**会变**，微调一次就要重训；而且我需要**可溯源**，得指出答案来自哪段文档。这两条 RAG 天然满足。" | **做过真项目** |

**差距在最后那句"我先排除了"**。好答案展示的是**淘汰过程**，不是结论。

记住这个公式：

> **情境 → 我考虑了几个选项 → 我排除了哪些、为什么 → 剩下这个的代价是什么**

"代价"那一项特别加分——**任何选择都有代价，能说出代价的人才是真做过选择的人。**

## 二、概念辨析题（4 道）

### Q1：Agent 和 Workflow（工作流）有什么区别？

**想听什么**：这是区分"跟风党"和"理解者"的第一道题。混了会显得外行。

**差答案**："Agent 更智能。"

**好答案**：

> 关键区别是**路径由谁决定**。Workflow 的步骤是人预先定好的，Agent 的下一步是模型临场决定的。
>
> 我在项目里**两者都用**了：意图识别到路由这一段是 Workflow（关键词匹配，确定性的）；意图定下来之后，让 LLM 自己决定调哪个工具、要不要多轮调用，这是 Agent。
>
> **Anthropic 有句话说"能用工作流解决的别上 Agent"**，我认同——因为 Agent 的自主性有代价：不可预测、难测试、token 消耗大。所以我只在"确实需要临场判断"的地方用 Agent。

**可追问的下一层**：

- 追问："那你怎么测 Agent？"
  → 转 Q12（测编排不测输出）
- 追问："如果 LLM 判断错了怎么办？"
  → 答降级：意图分类有三级降级（强关键词 → LLM → 弱关键词），不把单点押在模型上

### Q2：Function Calling 和 MCP 是什么关系？

**想听什么**：这是 MCP 最常被问、也最容易答混的一题。

**差答案**："MCP 就是一种 Function Calling。"（错）

**好答案**：

> 它们是**两个层次**的东西。
>
> **Function Calling 是模型的一种能力**——模型能输出"我要调 `get_weather`，参数是 city=广州"这种结构化结果。注意模型**不执行**任何函数，它只输出调用意图，真正执行的是我的代码。
>
> **MCP 是工具接入的协议**——它管的是"**有哪些工具、怎么描述、怎么发现、怎么调**"。
>
> 一句话：**Function Calling 回答"调哪个"，MCP 回答"有哪些"。** 前者是个人会打电话的能力，后者是电话网的标准。

**可追问的下一层**：

- 追问："那你为什么需要 MCP？直接 Function Calling 定义工具不行吗？"
  → 答：可以，但工具定义就**硬编码在 Agent 里**了。MCP 让工具跑在独立进程，**增删工具 Agent 代码零改动**，重启自动重新发现。

### Q3：RAG 和微调怎么选？

**想听什么**：淘汰过程的推导，不是结论。

**好答案**（用第一节那个结构）：

> 我选了 RAG，但**先排除了微调**。理由有三条，都是我的场景约束：
>
> ① **知识会变**。我的知识库是广州景点/美食/交通攻略，会更新。微调一次就要重训，RAG 改文档就行。
> ② **需要可溯源**。我要能指出"这个答案来自哪段文档"。微调是把知识内化进权重，说不清来源。
> ③ **成本**。微调要算力和数据标注，RAG 只要我对文档生成一次 embedding。
>
> **微调的代价我也清楚**：它更适合"固定说话风格"而不是"记住事实"。所以如果哪天需要统一的输出风格，那该上微调。**这两件事不冲突，是分工。**

### Q4：什么是幻觉？怎么解决？

**想听什么**：是否理解这是**固有特性**而不是 bug。

**好答案**：

> 幻觉是模型一本正经编造不存在的事实。**关键是它不是 bug，是固有特性**——模型的本质是预测下一个最可能的词，不是查数据库。所以它在不知道的时候，**会生成一个"看起来最像答案"的东西**，而不是说"我不知道"。
>
> 我的项目里踩过一次：单轮对话时模型会凭训练知识编造"明天 3 月 15 日"这种日期。
>
> 解法是**两层**：
> ① **接真实数据源**——让天气走工具而不是让模型回忆。这是治本。
> ② **提示词硬约束**——系统提示词里明确写"禁止编造数据，工具未返回的数据一律不得臆造"。
>
> 补一句：**第二层只是"建议"不是"保证"**。真要保证，得在生成之后加校验。

**加分点**：最后那句"提示词是建议不是保证"——它会立刻把你和只会背"用提示词约束"的人区分开。

## 三、架构选型题（4 道）

### Q5：为什么用 LangGraph 而不是直接写 if-else？

**差答案**："因为 LangGraph 更先进。"

**好答案**：

> 因为 Agent 需要**循环**：判断 → 调工具 → 再判断。if-else 表达循环会很别扭，而且流程一变就要改代码。
>
> LangGraph 用图建模，我项目里就四个节点：`classify_intent`（识别意图）、`agent`（LLM 决策）、`tools`（执行工具）、`handle_error`（兜底）。**循环就是两条边**：
> ```
> agent --有 tool_calls--> tools --回流--> agent
> agent --没有 tool_calls--> END
> ```
>
> 还有两个实际好处：**图可以画出来给人看**，**节点和边是明确对象所以可以被测试**。
>
> **但我不会在所有地方都用它。** 如果流程是固定的（取数据 → 生成 → 返回），我直接写函数——那种场景上 LangGraph 是过度设计。

### Q6：你的系统怎么保证稳定？

**想听什么**：有没有"故障是常态"的意识。

**好答案**：

> 我的设计前提是"**每个外部依赖都会挂**"。所以做了四层降级：
>
> | 层 | 挂什么 | 降级到哪 |
> |---|---|---|
> | 1 | Embedding API | 本地伪向量（n-gram hash，维度恒定 1024） |
> | 2 | 意图分类 LLM | 关键词匹配 |
> | 3 | 生成 LLM | 图内兜底节点返回友好话术 |
> | 4 | 以上全部 | 最外层 catch 一切，**接口永不 500** |
>
> 另外数据源也是可切换的：和风天气挂了自动切 Open-Meteo，Tavily 挂了切 DuckDuckGo。
>
> **但我要主动说一个不足**：第 4 层兜底节点**实际上是不可达的**，我后来才发现（详见第六节）。所以严格说，我的"四层"里有一层是纸面上的。

**这段为什么强**：**主动暴露不足**。面试官最烦的是"我的系统完美"。你说出"有一层是纸面上的"，反而证明你真的查过自己的代码。

### Q7：多租户的数据隔离怎么做？

**好答案**：

> 关键判断是：**隔离做在查询层，不做在应用层**。
>
> 每条知识分块都存 `user_id`，检索 SQL **强制**带上过滤：
> ```sql
> WHERE user_id = :user_id AND embedding IS NOT NULL
> ```
> 而不是"取回来再在 Python 里过滤"——应用层过滤有两个问题：**性能差**（多取了数据）和**容易漏**（忘了写一句 if 就漏了）。
>
> 还有个架构决策值得说：**我的用户私有检索没走 MCP，走的是本地工具**。因为 MCP 跑在独立子进程，`contextvars` 跨不了进程，拿不到 `user_id`。所以我把工具分了两类：**无状态的公共工具（天气/资讯/公共知识库）走 MCP，有用户态的私有工具走本地**。

### Q8：为什么用 pgvector 不用 Milvus？

见 B 辑的详细版本，这里给面试版：

> **因为量级**。我知识库只有 16 个文档、33 个分块。为了 33 个分块运维一个独立向量数据库，投入产出比不成立。
>
> 用 pgvector 有三个具体好处：① **零新增组件**（复用已有的 Postgres）② **事务天然一致**（向量和业务数据同库，不会"向量写了但业务回滚"）③ 检索就是 SQL，不用学新 API。
>
> **什么时候该换**：向量到千万级以上、且对延迟有硬要求时。这一点我很清楚，所以这不是"我不会用 Milvus"，是"我这个量级不需要"。

## 四、工程细节题（4 道）

### Q9：你的 RAG 怎么分块的？

**想听什么**：有没有真的调过参数。

**好答案**：

> 300 字一块。策略是**先按段落切**（按 `\n\n` 分段），尽量在语义边界切开；只有单个段落超过 300 字时，才在段落内部按字符滑窗硬切。
>
> **为什么不机械地每 300 字一刀**：中文的语义单元本来就是"段"，在段落中间切，两个半块都语义残缺。
>
> 实测我的 16 个文档切成 33 块，平均 213 字，最长 299 字。

**关键加分句**（接下去说）：

> 不过这里我要坦白一个 bug：我配了 `overlap=50`（相邻块重叠 50 字防语义截断），**但它从来没生效过**。我后来做了个实验，`overlap=0` 和 `overlap=50` 的输出**逐字节相同**。原因是 flush 时保留的尾部，被紧接着的赋值覆盖了。
>
> 这个坑的教训不是"我写错了"，而是：**我配了一个参数，却从没验证过它生效。** 后来我把"改参数看输出变不变"变成了习惯。

### Q10：向量维度为什么是 1024？

> 两个原因。**一是模型支持**：智谱 embedding-3 支持自定义维度，1024 是精度和存储/速度的平衡点。**二是必须与数据库对齐**：我的 ORM 里列定义是 `Vector(1024)`，维度不符写库直接报错。
>
> **更重要的是我在客户端主动校验了维度**：
> ```python
> if len(v) != self.dim:
>     raise ValueError(f"向量维度 {len(v)} 与预期 {self.dim} 不一致")
> ```
> **为什么要在客户端拦而不是让数据库报错**：数据库报的是"类型不匹配"，很难一眼看出是"模型换了导致维度变了"。在入口拦下来，错误信息才指向真因。

### Q11：LLM 调用失败，你的 Agent 会怎样？

**这题如果诚实回答，效果极好**（因为答案暴露了一个真实缺陷）：

> 设计上是**路由到图内的兜底节点** `handle_error`，返回"AI 服务暂时不可用，请稍后重试"。
>
> 但我查代码时发现：**这个节点实际上是不可达的**。
>
> 原因：兜底的条件边 `_should_error` 只挂在 `classify_intent` 后面。而 `classify_intent` 自己已经把异常全 catch 了、降级到关键词匹配——**它永远不会产出 error 状态**。
>
> 真正的失败点是 `agent` 节点（LLM 调用）。它失败时确实返回了 `{"error": ...}`，但**出口接的是 `_should_continue`**，那个函数只看有没有 `tool_calls`，见末条没有就直接 `END`。
>
> 结果：**LLM 失败时 `answer` 是空字符串，兜底节点一次都没运行过。**
>
> 修法很简单：把 `_should_error` 也接到 `agent` 后面，**先判 error 再判 tool_calls**。

**为什么这题答成这样是加分而不是减分**：因为"**节点存在 ≠ 节点可达**"这个认知，比"我的系统有兜底"值钱得多。

### Q12：你怎么测一个 LLM 应用？

**想听什么**：这是 AI 岗最高频的"元问题"。

**好答案**：

> 核心原则一句话：**断言编排，不断言模型输出**。
>
> 因为模型输出内容不可复现（换个措辞、多句话都算"对"），断言它必然 flaky。但下面这些东西是**我的代码**，必须断言：
> - 意图路由对不对
> - 工具绑定对不对（该绑的时候绑了没）
> - 调用了几次、顺序对不对
> - 失败了有没有降级
>
> 具体实现上：我写了个假模型（FakeLLM），它**靠 `bind_tools` 传来的工具名来识别"我现在扮演哪个 Agent"**，而不是靠提示词文本。这样不调真 LLM 也能把整张图跑通。实测 81 个用例 49 秒全绿。
>
> 还有一个我觉得最值钱的测试思路：**把"坑"写成断言**。比如"关键词表里每个意图都必须有强关键词"、"注册表里的工具名必须和真实 `@mcp.tool()` 逐字一致"。这些约定破了代码不会报错，只会静默降级——所以必须用测试盯着。

**可追问**：

- 追问："怎么保证测试不偷偷连生产？"
  → 答：用 `respx` 拦截全部外部请求，**未匹配直接报错**。默认拒绝比写规范管用。

## 五、踩坑复盘题（3 道）

这三道是**分水岭**。前三类背一背能糊过去，这类糊不了——因为答案必须是具体的、有代价的、你亲手修过的。

### Q13：说一个你印象最深的 bug

**选这个（工程向，最有说服力）**：

> 最深刻的是一个"**不报错的 bug**"。
>
> 我给知识库切块器配了个 `overlap=50` 的参数，意思是相邻文本块重叠 50 字，防止一句话被从中间切断。docstring 里写着这个行为，配置项是真数字，代码里也有对应的行。
>
> **但它从来没生效过。** 我后来做了个决定性实验：把 overlap 改成 0，跑一遍——**输出和 50 时逐字节相同**。我又用 12 个全文档唯一的锚点词标记了一遍，结论是**相邻块之间的重叠恒为 0**。
>
> 根因是：flush 时保留的尾部 50 字，被紧接着的 `else: current = para` 直接覆盖了。只有"新段落本身超过 300 字"时才走另一条分支保住重叠——而正常文档段落都短于 300 字。
>
> **为什么它藏了那么久**：链路每一环看着都对——配置对、docstring 对、代码那行也对。而且**没有任何测试覆盖 `split_text`**。它对效果的影响是隐性的：跨边界的句子被切成两半，两半各自都不完整，但检索照样能返回东西。
>
> 教训：**"配置里写了的"和"代码里真的做了的"，是两件事。** 验证成本极低——把它调成 0 看输出变不变，一次运行就够了。

### Q14：有没有哪个设计是你后来发现做错的？

**选这个（架构向，展示自我审查能力）**：

> 有。我的项目里有**两条建表路径**，而且它们不一致。
>
> 一条是 Alembic 迁移（`alembic upgrade head`），另一条是 `init_db()` 里的 `create_all`。两条路径本该等价，但我发现：
> ① `init_db()` **漏了 `migrate_data => TRUE`** 这个关键参数（对已有数据的表必需）
> ② 它导入的模型列表**是过时的**（少了通知、行程、天气预警几个模型，而 `models/__init__.py` 里已经有 14 个了）
>
> **后果很隐蔽**：用 `create_all` 建的库，`alembic_version` 表是空的。之后想切到 Alembic，`upgrade head` 会从 `0001` 开始重放，直接报"表已存在"。
>
> 我的结论是**收敛成唯一路径**——以 Alembic 为准。如果一定要保留 `create_all` 作为快速起步，那必须紧跟一个 `alembic stamp head` 把版本对齐。

### Q15：如果重做一遍，你会改什么？

**这题最能体现成长**。好答案要**具体且有优先级**，不能是"我会更努力"。

> 三个，按优先级：
>
> ① **先写"不变式清单"，再写功能**。我现在的经验是项目里有四类"看不见的耦合"——**LLM 行为、图的可达性、配置是否生效、代码是否被调用**。这四类的共同点是**出错了也不报错**，日志干净、测试全绿、行为却和以为的不一样。所以我会在动手前先把"什么东西永远不许破坏"列清楚。
>
> ② **每条不变式配一个测试**。如果这一步前置，上面那两个 bug（overlap 静默失效、handle_error 不可达）**都当场就会被抓出来**——一个"改参数看输出"的测试、一个"断言节点可达"的测试就够了。
>
> ③ **可观测性跟功能同步做，不要最后补**。我是在后期才补的结构化日志和路由级指标，而之前所有问题排查都靠猜。
>
> 说个诚实的：我 26 天赶了 42 天的进度，**重做的话我大概率还是会先写功能**。所以真正可执行的不是"调整顺序"，而是加一条硬规则——
>
> **每做完一个功能问一句："这个东西如果坏了，我怎么知道？"答不上来就先别往下走。**

---

## 六、三个可以直接讲的真实事故

第五节的三道题，答案全在这里。这三件事的共同价值是：**它们都是"不报错的问题"**。

| 事故 | 表面现象 | 真相 | 一句话教训 |
|---|---|---|---|
| `handle_error` 不可达 | 图上明明有兜底节点 | 条件边挂错了节点，永远进不去 | **节点存在 ≠ 节点可达** |
| `overlap` 静默失效 | 配置项、docstring、代码都有 | 保留的重叠被下一行覆盖 | **参数存在 ≠ 参数生效** |
| 两条建表路径不一致 | 两种方式看着都能建表 | 一条漏参数、模型列表还过时 | **两种路径 ≠ 两种等价路径** |

**讲这三个的原则**：

1. **先讲现象，再讲怎么发现的**——面试官想知道你的排查路径，不只是结果
2. **主动说出"为什么它藏了这么久"**——这展示你对"什么样的 bug 最难抓"有判断
3. **给出可迁移的教训**，不要停在"我修好了"

**最关键的一点**：

> **这三个 bug 有一个共同特征：错了也不报错。**
> 日志干净、测试全绿、只是行为和你以为的不一样。
> 所以真正该建立的能力，是**主动给"看不见的耦合"配一个"看得见的验证成本"**。

这句话如果讲出来，基本可以宣告"这个人不是只会调 API 的"。

## 七、反客为主：问面试官什么

面试最后"你有什么想问的"，问对了能加分。AI 岗位推荐这几个：

1. **"你们的 Agent 现在是 Workflow 还是自主决策为主？"**
   → 展示你**知道这个区分**，而且关心架构而非只想入职
2. **"线上怎么发现模型答得不对？有人工反馈回路吗？"**
   → 展示你**有可观测性意识**
3. **"RAG 的知识库谁维护？更新频率大概是多少？"**
   → 展示你**关注落地成本**，不只是技术
4. **"如果模型挂了，产品上怎么兜？"**
   → 展示你**有故障意识**

**避免问的**："你们用什么大模型？"——这个问题太浅，且答案通常无所谓。

|---|---|---|---|
| 1 | Agent vs Workflow | 路径**谁定**：人定 = Workflow，模型定 = Agent | 概念 |

| 12 | 怎么测 LLM 应用 | **断言编排，不断言输出**；假模型靠绑定的工具名辨身份 | 细节 |

| 14 | 哪个设计做错了 | 两条建表路径不一致，漏了几参数、模型列表过时 | 踩坑 |
| 15 | 重做会改什么 | 先不变式 → 再验证 → 后功能；**"它坏了我怎么知道"** | 踩坑 |
