# 一个 AI Agent 项目真正用过的工具清单（含为什么选它、什么时候别选）

> 不是"2026 年最火的 20 个 AI 工具"那种清单。这是 `requirements.txt` 里逐行写下的真实选择，以及每个选择背后的取舍理由。

> 「AI Agent 工程化实战」· B 辑（工具箱）· B1
> 项目源码：**[Ticnix/weather-travel-recommend-system](https://github.com/Ticnix/weather-travel-recommend-system)**
> 基于气象大数据的出行推荐系统，AI Agent 全栈项目。FastAPI + PostgreSQL(TimescaleDB/pgvector/PostGIS) + Redis；
> LangGraph + MCP + Skill + RAG，对接 DeepSeek API；React/Vue 前后端分离，实现 3D 天气可视化、智能出行穿搭推荐。
> （项目仍在更新中）

---

## TL;DR

1. **工具清单的价值不在"有什么"，在"为什么没选另一个"**。网上那种"Top 20 AI 工具"你收藏了也不会用；但"为什么用 pgvector 不用 Milvus"这种判断，是能直接迁移的。
2. **本项目的依赖文件里，每一行都带注释说明理由**——包括为什么用 `>=` 而不是 `==`（运行依赖用 `>=`，测试依赖用 `==`，下面细说这个反直觉的区分）。
3. **一个反直觉的原则贯穿全清单**：能不加组件就不加。用 pgvector 而不是独立向量库、用 `NullPool` 而不是连接池、把规则写在 markdown 里而不是建个配置中心——**每个"不加"都是在省运维**。
4. 这份清单分四组：**编排 / 检索 / 模型接入 / 工程与测试**。每组都标了"什么情况下别选它"。

## 一、先说清楚这份清单的筛选标准

我见过太多"工具推荐"文章的问题：它们推荐的是**通用最优解**，但你需要的往往是**当前约束下的最省事解**。

所以这篇的每条都按同一个格式写：

```
【工具名】→ 为什么选它 → 什么情况下别选它 → 项目里的真实出处
```

最后一项最重要——**有出处才能验证**。所有引用都来自 `backend/requirements.txt` 和 `requirements-dev.txt`，那个文件里的注释是我自己写的，写的时候就说清了理由。

## 二、编排组：让 Agent 跑起来的那些

### LangGraph —— Agent 的状态机

```python
langgraph>=0.2.60
langchain-core>=0.3.0
```

**为什么选它**：

Agent 的本质是"**判断 → 调工具 → 再判断**"的循环。而 LangChain 早期的 LCEL 链是线性的（A→B→C），**表达不了环**。LangGraph 用图建模，能表达环、分支、条件路由：

```python
graph.add_conditional_edges("agent", _should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")   # 这条回流边就是"循环"
```

另一个不常被提起但很实际的理由：**图可以被画出来、也可以被测试**。第 10 篇里"断言编排不断言模型输出"能成立，就是因为图的节点和边是明确的对象。

**什么时候别选它**：

- 你的流程是**固定几步**（取数据 → 生成 → 返回）。这是**工作流**，直接写函数更清楚，上 LangGraph 是过度设计。
- 团队没人愿意读图。图的可视化优势建立在"有人看"的前提上。

**一句话**：**流程需要"模型自己决定走哪条路"时用 LangGraph；路径固定时用它反而是负担。**

### LangChain（Core + OpenAI 适配）

```python
langchain-openai>=0.3.0
```

**为什么选它**：项目**只用它的两小块**——消息类型（`HumanMessage` / `SystemMessage`）和 `ChatOpenAI` 这个统一客户端。**没有用 AgentExecutor、没有用 Chain、没有用 Memory 模块**。

这是我想强调的一点：**LangChain 不必整体采纳**。它的价值在于"消息类型 + 各家模型的统一接口"这两个基础件；至于编排，LangGraph 已经接管了。

**什么时候别选它**：如果你的需求只是"调一次 API 拿到文本"，直接 `httpx.post` 更透明。引入框架换来的是便利，代价是"出问题时多一层黑盒"。

### MCP + 它的 LangChain 适配器

```python
mcp>=1.0.0
langchain-mcp-adapters>=0.1.0
```

**为什么选它**：MCP 解决的是**工具接入的标准化**问题。项目里 7 个工具跑在独立进程（stdio 传输），增删工具时 **Agent 代码零改动**：

```python
# MultiServerMCPClient 拉取工具列表，进程内缓存，重启后自动重新发现
```

**什么时候别选它**：如果你的工具**需要用户的登录态**（比如"查我自己的订单"），**别走 MCP**。因为 MCP 跑在独立子进程，`contextvars` 跨不了进程，拿不到 `user_id`。

这是本项目最值钱的一条架构结论：**无状态公共工具走 MCP，有用户态私有工具走本地**。

**下面的坑必须知道**：stdio 模式下，MCP 子进程必须用 `sys.executable`：

```python
# 必须用 sys.executable（venv 的 Python），
# 否则系统 Python 没装 mcp 包 → ModuleNotFoundError
```

一个很小的细节，但会让人卡很久——因为报错信息指向的是"模块找不到"，而不是"你用错了解释器"。

## 三、检索组：向量、库与切块

### pgvector —— PostgreSQL 的向量扩展

```python
pgvector>=0.3.0
# SQLAlchemy 侧
sqlalchemy[asyncio]>=2.0.0
```

**为什么选它（而不是 Milvus / Qdrant / Chroma）**：

这个决策值得展开，因为它体现了"**选型看量级**"这个原则。

| | 独立向量库（Milvus 等） | pgvector |
|---|---|---|
| 检索性能 | 千万级以上更强 | 百万级够用 |
| 组件数 | **多一个要运维的数据库** | **零新增**（复用 Postgres） |
| 事务一致性 | 跨库要自己处理 | **同库天然一致** |
| 学习成本 | 一套新 API | 就是 SQL |

**本项目的量级**：16 个文档、33 个分块。**为了 33 个分块运维一个独立数据库？** 这个投入产出比显然不成立。

而且第四条（事务一致性）常被低估：用 pgvector，向量和业务数据在**同一个事务**里，不会有"向量写进去了但业务数据回滚了"这种状态。

**什么时候别选它**：

- 向量规模到**千万级以上**，且对检索延迟有硬要求 → 上专用向量库（Milvus / Qdrant）。
- 需要复杂的多向量/多模态混合检索场景。

**索引选择**：项目用 HNSW（`vector_cosine_ops`），做近似最近邻。数据量不大时，**HNSW 比引入 Milvus 更省运维**。

### 智谱 embedding-3 —— 向量生成

**为什么选它**：维度可指定（项目用 1024），且**与项目已有的智谱 Key 共用**（不用新开账号、不用新的账单）。

**配套的工程纪律**（这条比选谁更重要）：

```python
EMBED_DIM: int = 1024   # 必须与 ORM 的 Vector(1024) 严格对齐
```

并且在客户端**主动校验维度**，不符就不写库：

```python
if len(v) != self.dim:
    raise ValueError(f"向量维度 {len(v)} 与预期 {self.dim} 不一致")
```

**为什么要在客户端校验而不是让数据库报错**：因为数据库报的错是"类型不匹配"，很难一眼看出是"模型换了导致维度变了"。**在入口拦下来，错误信息才指向真因。**

### 自研切块器（不用 LangChain 的 splitter）

**为什么自研**：项目文档形态**极其统一**（16 个同构 Markdown）。用通用 splitter 要么引一个库、要么写一堆参数去覆盖它的默认行为。**形态统一时，50 行自研更可控。**

**什么时候别选自研**：文档格式一旦变杂（PDF、网页、表格混着来），马上换成成熟方案——**维护一个自己写的 splitter 不值得**。

⚠️ **这里有个血的教训**（第 13 篇）：自研的 `split_text` 有个 **`overlap` 参数从未生效**的 bug。`overlap=0` 和 `overlap=50` 输出逐字节相同。

**所以这条经验的真正版本是**：自研可以，但**必须给自研的每一行配断言**。否则你会得到一个"看起来很专业、其实某个参数是装饰品"的模块。

### RapidOCR + Pillow —— 别忽略这两个

```python
rapidocr-onnxruntime>=1.4.0   # 图片 OCR（离线兜底）
pillow>=11.0.0                # 图像处理
```

这两个不属于"AI 热点工具"，但注释里的权衡非常值得抄：

```python
# 图片文字识别（离线兜底）：没配视觉模型时，截图类图片靠它抽文字给文本模型。
# 开源、ONNX 运行时、不需要 PyTorch；未安装时该兜底自动关闭
rapidocr-onnxruntime>=1.4.0
```

```python
# 图像处理：行程海报要在生成的插画上精确叠字。
# 之所以不交给出图模型画字：带数字与专名的"09:00 白云山 25~33℃"它几乎必定出错，
# 而海报上写错温度/地点比不写更糟。
pillow>=11.0.0
```

**这两段是整份清单里我最满意的部分**，因为它们记录了**"什么不该交给 AI"**：

- OCR 用传统库而不是视觉模型，因为**要的是准确，不是聪明**
- 精度数字/地点用 Pillow 而非出图模型，因为**"海报上写错温度比不写更糟"**

**核心判断**：**AI 工具不是越多越好，而是"这个任务需要的是智能还是精确"。** 需要精确的地方，传统工具赢。

## 四、模型接入组：怎么调、怎么切、怎么兜底

### 只接 OpenAI 兼容格式的模型

```python
_PROVIDERS = {
    "deepseek": (...), "qwen": (...), "zhipu": (...),
    "openai": (...), "moonshot": (...), "ollama": (...),
}
```

**为什么只收这一类**：因为这样 `get_llm` **不用为任何厂商写分支**，统一走 `ChatOpenAI`，靠 `base_url + api_key + model` 三个字段切换。

**代价是明确放弃的**：注释里写了"仅收录 OpenAI 兼容格式的模型，**避免引入不兼容适配器**（如 Anthropic Claude）"。这是一次**主动的能力裁剪**——换来的是代码里零适配器。

**什么时候别这么做**：如果某个不兼容的模型是核心依赖（比如你就是需要 Claude 的长上下文），那这个取舍要重算。

### faster-whisper —— 语音转写

```python
faster-whisper>=1.0.0
```

**为什么选它**：

```python
# 语音转写（本地开源、**不需要任何 Key**）：faster-whisper 是 CTranslate2 版的
# Whisper，自带 PyAV 解码（因此不需要系统 ffmpeg）。
# 模型在 Dockerfile 里预下载，运行时不再依赖外网。
```

三个具体优点：① 不要 Key ② **不需要系统 ffmpeg**（自带解码）③ 模型预下载后**运行时不依赖外网**。

**第 ② 点是最值钱的**——"不需要系统 ffmpeg"意味着**不用改 Dockerfile 装系统包**，少一层环境依赖就少一类"在我机器上是好的"。

### 空 Key 优雅降级（不是工具，是模式）

```python
if not api_key:
    # 未配置 Key 时用占位符实例化，避免实例化即抛异常
```

**这个模式值得单独记**：未配 Key 时**不崩溃**，而是用一个占位符实例化，真调用时才报错、由兜底节点统一处理。

**为什么**：这样"没配 Key"不会让**整个服务启动失败**，只会让"需要它的那个功能"不可用。**故障范围被限制在一个功能内，而不是整个应用。**

## 五、工程与测试组：让"它现在是好的"可验证

### pytest 全家桶

```python
pytest==9.1.1            # 测试框架
pytest-asyncio==1.4.0    # 支持 async def 测试用例
pytest-cov==7.1.0        # 覆盖率统计
respx==0.23.1            # Mock httpx 请求（拦截和风/高德/Tavily）
```

**为什么 `pytest-asyncio` 必装**：这个项目**全是 async**（LangGraph、SQLAlchemy async、httpx）。没有它，测试根本写不了。

**`respx` 是这组里最重要的一个**，因为它的默认行为是"**未匹配的请求直接失败**"：

这意味着**测试不可能偷偷连生产 API**。一条"默认拒绝"的策略，比十条"记得写 mock"的规范管用。

### ruff —— 一个工具干两件事

```python
ruff==0.16.7             # Python 静态检查 + 格式化
```

**为什么选它**：**一个工具同时替代 flake8 + isort + black**。用 Rust 写的，快到可以放进 pre-commit 而不会让人烦。

**对个人项目尤其重要**：少一个工具就少一份配置、少一次"这个和那个的规则冲突了"。

### alembic —— 数据库迁移

```python
alembic>=1.13.0
```

**为什么必须有**：项目的表结构会演进（11 个迁移文件证明了这一点）。没有迁移工具，就得靠手工 SQL，而**"我本地改过了忘了同步到服务器"是必然会发生的事**。

**项目里的一个真实坑**（第 12 篇）：Alembic 的**回滚路径**（`downgrade`）才是坑最多的地方——因为它正常开发中几乎从不执行，bug 能潜伏很久。

## 六、一个反直觉的版本策略

这是我从两个依赖文件的差异里学到的，值得单独一节。

```python
# requirements.txt（运行依赖）
langgraph>=0.2.60
sqlalchemy[asyncio]>=2.0.0
```

```python
# requirements-dev.txt（测试依赖）
# ⚠️ 这里用 == 精确锁定版本，而 requirements.txt（运行依赖）用 >=。
# 原因：测试工具的行为会直接影响"CI 是否绿"，必须保证本地与 CI 完全一致。
pytest==9.1.1
respx==0.23.1
ruff==0.16.7
```

**反直觉在哪**：直觉上"生产依赖"更该锁死，"测试依赖"松一点无所谓。**但这里恰好相反。**

**理由**：测试工具的行为**会直接决定 CI 是红是绿**。如果 `pytest` 或它的插件自动升级后行为变了，你会在 CI 上遇到"本地全绿、CI 全红"的诡异情况——而这种问题的排查成本**远高于**定期手动升级的收益。

**一句话**：**哪个依赖的行为会影响"判断对错"，就锁死哪个。**

运行依赖松一点，是为了能吃到安全补丁和性能改进；测试依赖锁死，是为了让"绿"这个信号保持可信。

## 七、我没有用但值得知道的东西

一份诚实的清单应该包含"**我考虑过但没选、理由是什么**"，以及"**暂时没做、但知道该做**"。

| 工具 | 我没用的理由 | 什么时候该用 |
|---|---|---|
| LangChain 的 AgentExecutor | LangGraph 已接管编排，多一层抽象没收益 | 极其简单的单工具场景 |
| 独立向量库（Milvus/Qdrant） | 33 个分块，不值得多运维一个数据库 | 千万级以上向量 |
| Rerank 模型 | 列在升级计划里，当前 Top-5 直出够用 | 检索结果不够准时（见第 04 篇前瞻） |
| 混合检索（向量 + BM25） | 同上，在计划里 | 专有名词/缩写多的场景 |
| 微调 | RAG 已解决"知识"问题 | 需要固定"说话风格"时 |
| Docker（本地开发） | 本机缺 CPU 虚拟化支持，跑不起来 | 有虚拟化支持的环境 |

**最后一行值得说一下**：项目**生产用的是 Docker**（`docker-compose.yml` + 健康检查 + 自动回滚都是真的），但**本地开发不得已改用 Windows 原生**（`dev-user.ps1` 走 vite 热更新）。

**这不是"没做好"，而是"环境约束下的合理兜底"。** 讲项目的时候如实说清这一点，比假装全流程容器化要可信得多。

## 八、一份"选型自检表"

把本文的判断压缩成可以复用的问句。**引入任何新工具前问一遍**：

1. **它解决的是我当下的真问题，还是我想象中的未来问题？**
   （"33 个分块"不需要 Milvus）
2. **它会增加几个要运维的组件？**
   （pgvector 是 0 个新增；独立向量库是 +1 个数据库）
3. **我能不能用十行代码自己写出来？**
   （形态统一的切块器 → 能，自研；通用文档解析 → 不能，用库）
4. **这个任务是"要智能"还是"要精确"？**
   （要精确 → 传统工具：OCR 用 RapidOCR、叠字用 Pillow）
5. **它的默认行为是"失败时报错"还是"静默降级"？**
   （选前者，如 respx；静默的东西最难发现——见第 13 篇）
6. **它的版本升级会不会影响我的"对错判断"？**
   （会 → 锁死版本，如 pytest）
7. **如果它坏了，我怎么知道？**

**第 7 条是这份清单的守门人。** 答不上来的，先别加。
